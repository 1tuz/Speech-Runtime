# AGENTS.md — Speech Runtime

## 1. Project

Speech Runtime — универсальный локальный сервис для речевых моделей, аналог Ollama для обработки речи.

Один фоновый сервис предоставляет возможности независимым приложениям через единый API.

**Основные принципы:**
- Одна установка моделей для всех приложений.
- Повторное использование загруженных весов.
- Независимые конкурентные сессии.
- Явный выбор модели и операции клиентом.
- Локальная обработка без облачных зависимостей.
- Минимальное потребление ресурсов в простое.
- Модульная поддержка разных вычислительных движков.

Runtime не определяет сценарий использования, не выбирает модель по содержанию речи, не управляет LLM и не реализует логику голосовых ассистентов.

## 3. Architecture

Текущая гипотеза: небольшой управляющий сервис на macOS; Swift — основной кандидат. Изоляция вычислений процессами полезна, но количество воркеров, движков и их размещение определяются потребностями и измерениями. Клиентские сценарии остаются вне runtime.

Не представляй HTTP/WebSocket, LaunchAgent или отдельные воркеры ONNX/CoreML/MLX как принятый контракт. Сверяй архитектурные изменения с `docs/architecture.md` и статусами в `docs/decisions.md`.

Не добавляй второй язык, транспорт, базу данных или тяжёлую зависимость без доказанной необходимости.

## 4. Subagents

Максимально используй параллельных субагентов для независимых задач.

Предпочтительная модель:

`closerouter/deepseek/deepseek-v4.1-flash-1017`

Правила:

1. Проверь доступность модели в текущем окружении.
2. При использовании OMP настрой соответствующий `task.agentModelOverrides` для текущей сессии.
3. Используй максимально доступный параллелизм, когда задачи независимы.
4. Делегируй аудит библиотек, тесты, изучение моделей, лицензий и поиск дефектов.
5. Основной агент отвечает за архитектуру, объединение результатов и итоговые решения.
6. Не создавай субагентов ради формального количества.
7. Не допускай параллельного изменения одних файлов без координации.
8. Критические архитектурные выводы проверяй независимо.
9. Если модель недоступна, сообщи об этом. Не подменяй её незаметно.

Каждый субагент возвращает:
- Выполненные действия.
- Проверенные факты.
- Ссылки на код или результаты тестов.
- Выявленные проблемы.
- Предлагаемые изменения.

## 5. Work protocol

Для каждой существенной задачи:

**Research → Plan → Execute → Verify → Document**

### Research
- Определи текущее состояние проекта.
- Найди относящиеся к задаче исследования.
- Проверь существующие реализации.
- Выяви неопределённости и риски.

### Plan
- Составь короткий план.
- Определи независимые задачи для субагентов.
- Укажи критерии завершения.
- Не проектируй функциональность вне поставленной задачи.

### Execute
- Вноси минимально необходимые изменения.
- Предпочитай переиспользование проверенных библиотек.
- Избегай дублирования вычислительных движков.
- Не добавляй временные обходные решения без объяснения.

### Verify
- Выполни релевантные проверки.
- Сохрани результаты и команды воспроизведения.
- Отделяй фактические измерения от предположений.
- Не объявляй работу завершённой при непроверенных критических требованиях.

### Document
- Актуализируй существующую документацию.
- Не создавай дублирующие отчёты.
- Фиксируй принятые решения и причины отказа от альтернатив.

6. Проверить влияние фоновой транскрибации на потоковую.

## 7. ASR quality

Главный языковой приоритет — русский с английской IT-терминологией.

Примеры: Kubernetes, Istio, PostgreSQL, kubectl, Helm, CI/CD, Deployment, ingress, JVM.

Сравнивай модели на одинаковых аудиозаписях.

Основные метрики:
- WER / CER.
- Точность написания технических терминов латиницей.
- Term recall / precision.
- Задержка промежуточной и окончательной транскрибации.
- Real-time factor.
- Стабильность промежуточного текста.

Не выбирай основную модель по результатам исключительно английских тестов.

Не придумывай результаты отсутствующих измерений.

## 8. Runtime invariants

Обязательные технические требования:

- Клиент самостоятельно указывает модель и операцию.
- Неизвестная модель вызывает явную ошибку, а не скрытый переход на другую.
- Загруженная модель переиспользуется между клиентами, когда это технически возможно.
- Состояние одной сессии не влияет на другую.
- Batch-задача не должна бесконтрольно блокировать realtime-сессии.
- Обновление модели не должно прерывать активную сессию.
- Падение воркера не завершает основной сервис.
- Удаление используемой модели запрещено.
- Локальный API защищён от неавторизованных запросов.
- Аудио и транскрипты не записываются в логи по умолчанию.

## 10. Builds and testing

Предпочитай GitHub Actions для тяжёлых сборок, проверок совместимости и повторяемых тестов.

Локально выполняй только необходимые проверки, особенно если они требуют реального оборудования:

- CoreML / ANE.
- MLX / Metal.
- Загрузка моделей.
- Потребление памяти.
- Конкурентность вычислений.
- Измерение задержек.

Не выполняй полную пересборку проекта после каждого небольшого изменения.

Не скачивай повторно уже имеющиеся модели.

Сохраняй воспроизводимые команды и результаты экспериментов.

## 11. Definition of Done

Задача завершена, только если:

1. Выполнены её явные требования.
2. Нет незаявленных архитектурных изменений.
3. Релевантные проверки пройдены либо ограничения честно описаны.
4. Документация актуальна.
5. Результат можно воспроизвести.
6. Основной агент проверил и объединил результаты субагентов.

В финальном ответе кратко укажи:
- Что сделано.
- Что проверено.
- Что осталось непроверенным.
- Какие решения требуют дальнейших измерений.

Не выдавай предполагаемую работоспособность за подтверждённую.
