# Адаптация к терминам: контекст, hotwords, эмбеддинги

Даты: 2026-10-28/29 (разделы 1–2, Apple M5 Pro, 48 ГБ) и 2026-11-03/04
(раздел 3a, Apple M4, 16 ГБ). Все прогоны — на
`dev` (321 реплика, три встречи Veche-bench); `test` не использовался ни для
настройки, ни для выбора порогов.

## 1. Контекст Qwen3-ASR: пустой, релевантный, отвлекающий

`mlx-qwen3-asr` передаёт `context` в system-prompt — тот же механизм, что
официальный `context` Qwen3-ASR. Три прогона на одних и тех же 321 репликах,
модель `Qwen/Qwen3-ASR-0.6B` fp16.

| Контекст | WER | CER | term recall exact | term precision | F1 |
|---|---|---|---|---|---|
| пустой | 21.47 % | 8.47 % | 25.0 % | 83.3 % | 38.5 % |
| релевантный (12 IT-терминов) | 22.06 % | 8.83 % | **27.5 %** | 78.6 % | 40.7 % |
| отвлекающий (медицинские термины) | 22.03 % | 9.25 % | 7.5 % | 75.0 % | 13.6 % |

Релевантный контекст даёт +2.5 п.п. term recall exact, но +0.59 п.п. WER.
Отвлекающий контекст обваливает recall до 7.5 % — модель начинает писать
медицинские слова вместо IT-терминов. На 40 вхождениях терминов разница
в 2.5 п.п. — это одно вхождение, то есть в пределах шума; вывод «контекст
помогает» на этом объёме не подтверждён.

## 2. Nemotron: decode-time hotword biasing

`setCustomVocabulary` (per-token log-prob bonus 4.5, тир 560 мс, `ru-RU`).
Словарь: 12 IT-терминов, по одному в строке.

| Вариант | WER | CER | term recall exact | term precision | case accuracy |
|---|---|---|---|---|---|
| без словаря | 24.90 % | 10.41 % | 37.5 % | 94.1 % | 100 % |
| со словарём | 25.18 % | 10.91 % | **40.0 %** | 94.1 % | 93.8 % |

Изменения затронули 25 реплик из 321. Примеры перестрела (изменённые токены):

| Было | Стало |
|---|---|
| `Лиа привет` | `I apриet` |
| `дедлайн` | `deadlain` |
| `пятнадцатого` | `p` |
| `як … раз` | `is … res` |
| `интервью` | `iнtervью` |

То есть biasing действительно применяется (выход меняется, term recall растёт),
но greedy-декод без бима коммитит забустенный токен, и на частых словах
возникает порча текста. Прирост term recall (+1 вхождение) меньше, чем ущерб
от перестрела. Для русского нужен список терминов, проверенный на перестрел,
и, вероятно, меньший boost — это отдельный опыт.

Требование движка выполнено: в бандле 560 мс есть `decoder_joint.mlmodelc`
(logits-путь), поэтому bias не отключается молча.

## 2b. Parakeet: vocabulary boosting через отдельный CTC-энкодер

Подход 2 из документации FluidAudio: TDT-энкодер + отдельный CTC-110M,
рескоринг каждого окна. Прогон через `SlidingWindowAsrManager` (окно 11+2+2 с),
тот же dev, тот же список из 12 терминов.

| Вариант | WER | CER | term recall exact | term precision | F1 | RTF |
|---|---|---|---|---|---|---|
| батч-прогон (`AsrManager`) | 12.42 % | 4.21 % | 12.5 % | 80.0 % | 32.0 % | 0.0126 |
| sliding window, без словаря | 12.42 % | 4.21 % | 12.5 % | 80.0 % | 32.0 % | 0.0126 |
| sliding window + CTC-рескоринг | 12.56 % | 4.24 % | 12.5 % | **57.1 %** | 29.6 % | **0.0455** |

Два вывода:

1. **Стриминговый путь воспроизводит батч побайтово** на этих репликах
   (WER, CER, S/D/I и все терминные счётчики совпадают). Значит окно 11+2+2 с
   на коротких репликах не деградирует, и разницу в предыдущих замерах давала
   не схема обработки, а подсказка языка.
2. **CTC-рескоринг не помог и утроил время.** Recall не изменился (12.5 %),
   precision упал с 80 % до 57.1 % — то есть появились лишние терминные формы
   без единого нового верного попадания. RTF 0.0126 → 0.0455 (3.6×).

Это согласуется с Nemotron: оба механизма на 40 вхождениях терминов не дают
прироста, а на Parakeet ещё и стоят втрое дороже. Причина, вероятно, в том, что
12 терминов из головы списка почти не встречаются в dev; проверять boosting
надо на списке, собранном из реальных ошибок этого корпуса.

## 3. Эмбеддинги: правила против семантики

`Qwen3-Embedding-0.6B`, MLX (mxfp8 для базовой оценки, 4-bit DWQ для LoRA).
94 пары «наблюдавшаяся ошибка ASR → правильный термин» из dev, собранные
`make_error_pairs.py` по выравниванию гипотез четырёх систем (parakeet 34,
nemotron 24, gigaam 21, whisper 15).

| Подход | Recall@1 | Recall@5 | Recall@10 | MRR |
|---|---|---|---|---|
| точное совпадение с формой словаря | 3.2 % | — | — | — |
| символьное расстояние (порог 0.5) | — | — | — | 44.6 % accuracy@1 |
| эмбеддинги, базовая модель | 14.3 % | 33.9 % | 44.6 % | 0.224 |
| эмбеддинги, после LoRA (40 шагов) | **44.6 %** | **58.9 %** | **71.4 %** | **0.542** |

LoRA: r=8, alpha=16, targets `q_proj/k_proj/v_proj/o_proj`, InfoNCE,
temperature 0.05, batch 8, lr 2e-5, 38 обучающих пар, 40 шагов, `train_loss`
0.858. Адаптер сохранён (`adapters.npz`, 9 234 486 байт, sha256 `8aa8aa99…`) и
**перезагружен**: метрики после перезагрузки совпали с метриками после обучения
(`recall@1` 0.4464, MRR 0.54240 в обоих).

Повторный прогон обучения с теми же параметрами дал `train_loss` 0.8583 вместо
0.8584 и MRR 0.54240 вместо 0.54228 при том же `recall@1`. Значит обучение не
детерминировано на уровне четвёртого знака: `recall@1` воспроизводится, MRR —
нет. Для вывода «LoRA помогает» это не важно, для регрессионных порогов — важно.

Снижение training loss не является критерием: критерий — метрики на 56
отложенных парах, они выросли с 0.143 до 0.446 по recall@1.

## 3a. Parakeet Ultra: LoRA-корректор на парах гипотез

Дата: 2026-11-03/04. Машина: Apple M4, 16 ГБ (MLX). Qwen3-0.6B + LoRA
(unsloth, r=16, alpha=16, lr 5e-5, 3 эпохи, batch 2 × grad-accum 4, max_seq
1024). Обучающие пары — «гипотеза Parakeet Ultra → референс» из **других**
встреч; оценка leave-one-meeting-out на dev (321 реплика). Раннеры:
`runners/correction_pairs.py`, `correction_lora.py`, `correction_apply.py`,
`correction_report.py`; артефакты — `results/correction/parakeet-lora-*.json`.

| Отложенная встреча | пар train / valid | WER до | WER после | Δ WER | изменено реплик | исправлено / добавлено ошибок |
|---|---|---|---|---|---|---|
| `2-one-to-one` | 271 / 50 | 4.85 % | 5.10 % | +0.26 п.п. | 5 из 50 | 1 / 2 |
| `5-it-product` | 211 / 110 | 8.89 % | 11.13 % | +2.25 п.п. | 18 из 110 | 0 / 21 |
| `7-bi-platform` | 160 / 161 | 12.79 % | 18.49 % | +5.70 п.п. | 44 из 161 | 1 / 88 |
| **суммарно** | 642 / 321 | **10.42 %** | **14.24 %** | **+3.82 п.п.** | 67 из 321 | **2 / 111** |

Механика работает (модель меняет ровно те реплики, где ошибки, и не трогает
остальные), но направление неверное: 2 исправления против 111 новых ошибок.
Стоимость: 0.60 с на реплику (p50 0.575, max 0.843; 8 реплик после прогрева,
жадная генерация), загрузка 1.53 с, пик MLX 1.45 ГБ, RSS 1.80 ГБ
(`results/correction/parakeet-lora-apply-latency.json`). ASR на той же машине —
0.13 с на реплику, то есть корректор добавляет ~4.7× ко времени и 1.5 ГБ памяти
при отрицательном эффекте на WER.

Отличие от раздела 3: там LoRA обучалась на **текстовых парах эмбеддингов**
(сопоставление похожих написаний) и показала рост recall@1 на отложенных парах.
Здесь LoRA обучается на **парах «гипотеза → референс»** и должна была переписать
текст. Вывод: генеративная коррекция на 0.6B-модели при 160–271 обучающих парах
не обобщается на новую встречу — она переобучается на способ правки, а не на
домен. Для коррекции нужны либо на порядок больше пар, либо правила/словарь, а
не модель.

## 4. Правила замены: цена ложных срабатываний

Порог и margin заморожены на dev, поэтому цифры ниже — dev, а не test.

| Правило | Замен | Исправлено ошибок | Ложных (портит верный токен) | Неверных | WER |
|---|---|---|---|---|---|
| символьное, t=0.25 | 7 | 1 | 4 (1.4/1000 слов) | 2 | 21.47 → 21.57 % |
| символьное, t=0.3 | 14 | 1 | 8 (2.8/1000) | 5 | 21.47 → 21.71 % |
| символьное, t=0.4 | 128 | 1 | 106 (37.5/1000) | 21 | 21.47 → 25.15 % |
| эмбеддинги + локализация, t=0.5 | 3 | 0 | 2 (0.7/1000) | 1 | 21.47 → 21.54 % |
| эмбеддинги + локализация, t=0.6 | 0 | 0 | 0 | 0 | 21.47 % (без изменений) |

Соотношение исправлений к порче при любом пороге хуже единицы: одно исправление
на 4–106 ложных замен. При пороге, где порчи почти нет (t=0.6 для эмбеддингов),
правило не делает ничего. Причина в данных: в dev всего 40 вхождений терминов,
а большинство подстановок — это слова общего языка, ошибочно похожие на
термин (`могу → MongoDB`, `тогда → Node.js`, `впихнуть → апрувнуть`).
Правило «не менять при неуверенности» реализовано и работает: при t=0.6
и выше замена не выполняется вовсе, и WER остаётся ровно прежним.

Вывод: на 94 парах и 40 вхождениях терминов коррекция по словарю не окупается.
Нужен словарь, проверенный на перестрел, и больше терминных вхождений в dev.

## 5. ASR-LoRA: заблокировано библиотекой

LoRA декодера Qwen3-ASR-0.6B через `mlx-tune` 0.6.0 не запускается: `mlx-audio`
0.6.3 конвертирует `mx.array` в `numpy` внутри `Qwen3ASRAudioTower.__call__`
(строка 354), а это запрещено внутри `mx.grad`. Тот же класс ошибки, что был в
`last_token_pool` у эмбеддингов, но здесь он требует переписывания нарезки на
чанки и масок на полностью `mx`-операции. Минимальный сбой, версии и причина —
[ASR_LORA_BLOCKED.md](ASR_LORA_BLOCKED.md). Ветка остановлена по условию задачи:
собственный trainer не разрабатывался.

## 6. Ограничения

- Все пороги выбраны на 321 реплике; доверительные интервалы на таком объёме
  шире любого наблюдённого эффекта.
- LoRA обучена на 38 парах — этого достаточно, чтобы показать механику и
  отсутствие поломки перезагрузки, но не чтобы утверждать перенос на другие
  домены.
- Qwen-контекст проверен на одной модели; у GigaAM и Parakeet такого
  параметра нет.
- Nemotron-словарь — 12 терминов, вес по умолчанию; сетка весов не снималась.
- Патч `last_token_pool` в `mlx_embeddings` (ветвление через `mx.where`)
  нужен, чтобы обучение вообще шло; он меняет только форму вычисления, не
  результат инференса, и записан в `experiments/runners/patches/`.
