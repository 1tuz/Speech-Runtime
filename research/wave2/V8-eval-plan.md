# V8 — План проверки runtime и методика оценки русского IT-языка

Статус: готово (вторая волна, исследование — не реализация). Дата: 2026-10-25.
Область: как измерять (а) качество распознавания русского IT-языка, (б) свойства самого runtime.
Реализация не входит. Все числовые пороги приёмки — **предлагаемые**, не факты.
Собственные измерения помечены явно (§2.6); всё остальное — проверка по коду и первоисточникам (см. таблицу ниже).

Разделение, которое держится во всём документе:
- **Контур A — решающие эксперименты** (§8): проводятся ДО фиксации архитектуры и модели; их результат меняет решения в `00-draft-architecture.md`.
- **Контур B — приёмка готового runtime** (§9): регрессионные гейты, которые прогоняются на каждом релизе после того, как архитектура выбрана.

## Итог

1. **Публичного русского code-switching / IT-набора не существует** (проверено поиском по HF: `code-switch*` даёт только ar/en, zh/en, si/en, ca/es; русских нет). Датасет ru-IT придётся записывать самим — это не «улучшение», а обязательный артефакт, без него сравнивать модели по нашей главной метрике нечем.
2. **Готовый харнесс WER уже есть в speech-swift** (`asr-bench`: `Sources/AsrBenchmark/`): нормализатор, WER/CER с S/I/D, `--isolated` для честного peak RSS через `phys_footprint`/`ledger_phys_footprint_peak`, загрузка произвольного TSV-манифеста `<путь>\t<текст>`. Это снимает необходимость писать свой WER-раннер: наш датасет подключается манифестом.
3. **Готовый харнесс диаризации тоже есть** (`DiarizationBench`: RTTM-референсы, collar 0.25 с по умолчанию, DER + JER, разбивка DER по числу спикеров) — его можно взять как есть, нужны только русские RTTM.
4. **Методика keyword-биасинга у FluidAudio пригодна как образец, но её метрики «Dict Pass» и «Vocab Recall» измеряют разное, и ни одна не подходит для русского напрямую**: «Dict Pass (Recall)» — это детекция ключевого слова CTC-споттером (механизмом биасинга), а «Vocab Recall» — вхождение слова в финальный текст, посчитанное регуляркой `\b…\b` по lowercase-нормализованным строкам. Для нашей задачи нужна трёхуровневая классификация (точная латиница / кириллическая транслитерация / искажение), которой там нет, и «Dict Pass»-метрика полезна как отдельный индикатор — «сработал ли механизм подсказки вообще».
5. **Open ASR Leaderboard русский не покрывает** и его нормализатор содержит только `EnglishNumberNormalizer` — русскую нормализацию чисел (`num2words(lang="ru")`) и ё→е придётся добавлять самим; ссылаться на «методику лидерборда» можно только в части инвариантов (нормализация до подсчёта, RTFx = аудио/время инференса в одном прогоне).
6. **Объём набора определяется не «часами», а числом терминов и числом высказываний**: при 500 высказываниях парный bootstrap различает разницу WER ~1.5 п.п. с мощностью ≈0.97, а 1.0 п.п. — только с 0.71 (мой прогон симуляции, §2.6). Для терминов при 400 вхождениях полуширина 95 % ДИ ≈±4.5 п.п. (при доле 0.7), то есть набор на 3–5 часов различает только крупные различия по терминам, а не тонкие. Отсюда целевой объём: test 5–7 ч с ≥ 400 вхождениями терминов.
7. **Разделение «до архитектуры» и «после» проходит по одному признаку**: всё, что зависит от способа доставки аудио (латентности partial/final, поведение под смешанной нагрузкой, стоимость N сессий), меряется только на прототипе транспорта; всё, что зависит от модели (WER, term recall, пунктуация), меряется офлайн и не требует runtime вообще.
8. Лицензионная развилка уже сейчас: OpenSTT — `CC-BY-NC` (коммерческое использование только по договору), Common Voice с октября 2025 доступен только через Mozilla Data Collective, Golos на HF без поля license, Sova RuDevices и FLEURS — `cc-by-4.0`, RuLS — public domain. Набор, собранный на OpenSTT, нельзя использовать в коммерческом продукте и нельзя класть в публичный репозиторий как тест-фикстуру.

## 1. Два контура оценки

| | Контур A: решающие эксперименты | Контур B: приёмка runtime |
|---|---|---|
| Когда | до фиксации архитектуры/модели | на каждом релизе |
| Что решает | выбор модели, движка, схемы конкурентности, нужен ли биасинг | «не стало хуже», «укладываемся в бюджет» |
| Данные | ru-IT dev + публичные прокси | ru-IT test (заморожен) + синтетика |
| Стоимость прогона | часы-дни, вручную | минуты, в CI |
| Формат результата | отчёт с CI, решение | pass/fail + числа в артефакте |

Правило: **ни один порог из контура B не выводится из контура A**. Контур A отвечает на вопрос «какая модель», контур B — «не сломали ли мы её».

### 2.2 Целевой состав ru-IT

Четыре регистра, потому что они по-разному ломают ASR:

| Регистр | Что записываем | Зачем | Доля по времени |
|---|---|---|---|
| R1. Диктовка (dictation) | один диктор, близкий микрофон, команды и конфиги вслух | основной сценарий «наговорил — получил текст»; чистая акустика, вся сложность в лексике | 30 % |
| R2. Созвон (meeting) | 2–4 участника, гарнитуры/ноутбучные микрофоны, перебивания | диаризация + дальнее поле + спонтанность | 35 % |
| R3. Спонтанная речь (standup/объяснение) | один-два диктора, без сценария, «объясни, почему упал под» | disfluencies, самокоррекция, быстрый темп | 20 % |
| R4. Команды и код (command) | `kubectl get pods -n prod`, `psql -c "select ..."`, пути, флаги, версии | латиница, дефисы, регистр, цифры — самый жёсткий тест на термин | 15 % |

Требования к покрытию:
- ≥ 10 дикторов в R1/R3, ≥ 8 разных пар/троек в R2 (иначе speaker-ID EER не посчитать);
- ≥ 30 % дикторов — неродной русский или с выраженным акцентом `[INFERENCE]` (акценты — типичная причина деградации терминов; в публичных наборах они недопредставлены);
- микрофоны: минимум 3 класса (гарнитура, встроенный ноутбучный, петличка/телефон), в R2 — минимум 20 % сегментов с разносом «дальний участник»;
- шум: ≥ 15 % сегментов с бытовым фоном (кафе/офис open space), ≥ 10 % — с клавиатурой/вентилятором.

Размер: ≥ 300 уникальных терминов, ≥ 1500 вхождений в наборе, ≥ 400 вхождений в test-сплите. Обоснование числа — §2.6.

### 2.4 Протокол записи

1. **Сценарии** пишутся заранее как скрипты-подсказки (не зачитываемый текст): для R1 — список команд на экране, для R3 — 5 вопросов на тему, для R4 — 10 команд в терминал вслух.
2. **Двойной проход R4**: каждую команду диктор произносит дважды — «как написал бы в чате» (латиница: `kubectl get pods`) и «как сказал бы голосом» (`кубэ-си-ти-эл гет поды`). Это даёт матрицу «произношение → ожидаемая запись».
3. **Аудио**: WAV PCM 16-bit, 48 кГц (даунсэмплинг до 16 кГц делает потребитель), mono, отдельный файл на сегмент + непрерывная дорожка на встречу. Часы всех устройств синхронизируются до начала (для R2), в начале каждой сессии — хлопок как маркер.
4. **Метаданные на сегмент** (JSONL): `segment_id`, `recording_id`, `register` (R1–R4), `speaker_id`, `mic_class`, `noise_class`, `duration_s`, `terms[]` (id из `terms.yaml` с позициями), `expected_latin[]`, `notes`.
5. **Согласие и персональные данные**: письменное согласие на запись и на использование в внутренних замерах; имена/клиенты/хосты в речи заменяются на вымышленные на этапе сценария, не постфактум.
6. **Версионирование**: `ru-it-v0.1` и т. д.; test-сплит замораживается после первой публикации чисел и не меняется (иначе числа несравнимы между релизами).
7. **Сплиты**: dev (30 %) / test (70 %) — **по дикторам и по встречам**, не по сегментам. Иначе утечка: одни и те же голоса в dev и test завышают качество и ломают speaker-ID EER.

### 2.5 Разметка и нормализация референса

Это самое спорное место, и его надо зафиксировать ДО первого замера (иначе получим расхождение 3.1 vs 5.13 п.п., как у Sber и Mistral на FLEURS ru).

**Двухслойный референс.** Каждый сегмент хранит два текста:
- `ref_verbatim` — как произнесено, с дисфluencies, без пунктуации, латиница в том виде, в каком она ожидается на выходе;
- `ref_normalized` — результат детерминированного нормализатора (код в репозитории, не «на глаз»).

**Правила нормализации (v1, предлагаемые):**

| Правило | Решение | Почему |
|---|---|---|
| Регистр | lowercasing для WER; отдельный замер case-sensitive для терминов | иначе пунктуация/регистр моделей с e2e-выходом штрафуются дважды |
| Пунктуация | удаляется для WER; отдельная метрика P-F1 | то же |
| `ё` | `ё → е` в обеих сторонах | модели без `ё` в словаре (GigaAM CTC — 33 буквы без ё) иначе получают систематический штраф |
| Латиница | **сохраняется как есть**, не транслитерируется | это наша целевая метрика, её нельзя размывать |
| Транслит как допустимый вариант | **не** допустим в WER; учитывается отдельным классом в term-метрике | иначе WER «прощает» главный дефект |
| Числа | цифры → слова по `num2words(lang="ru")` **в обеих сторонах** | «1.29» vs «один двадцать девять» — иначе модель наказывается за формат |
| Аббревиатуры | `k8s` = `kubernetes`? — **нет**, разные термины; `CI/CD` = `ci cd` = `ci-cd` — **да** | первое — разные сущности, второе — разная пунктуация одного и того же |
| Дефис/пробел внутри термина | `postgresql` = `postgre sql`? — **нет**; `ci cd` = `cicd`? — **да** | компромисс: склейка допустима, разрыв на два слова — нет |
| Филлеры (`э`, `ну`, `как бы`) | удаляются из гипотезы, если их нет в референсе; в референсе сохраняются как есть | иначе штраф за разговорность |
| Дисфluencies в R3 | сохраняются в `ref_verbatim`; в `ref_normalized` — удаляются по фиксированному списку | спонтанная речь иначе даёт несравнимый WER |

**Допустимые варианты термина.** Для каждого термина задаётся множество приемлемых написаний (`accept`): например для `PostgreSQL` — `{postgresql, postgres}`, для `CI/CD` — `{ci/cd, ci cd, cicd, ci-cd}`. Это множество используется **только** в term-метрике, не в WER.

**Разметка терминов.** Автоматически по словарю + ручная валидация: скрипт находит вхождения всех терминов и их транслитов в `ref_verbatim`, разметчик подтверждает/правит. Хранится как `terms[]` с `char_start`, `char_end`, `term_id`, `spoken_form` (latin / translit / mixed).

## 3. Метрики

### 3.1 Batch ASR: WER / CER

- **WER** — по нормализованному тексту (§2.5), токенизация по пробелам, Levenshtein с S/I/D. Референс реализации — `WER.swift` в speech-swift (проверено, см. таблицу).
- **CER** — по нормализованному тексту с удалёнными пробелами. Для русского CER полезен как «страховка»: при слипании слов WER взрывается, CER — нет.
- Обе метрики — **corpus-level** (сумма ошибок / сумма слов), не среднее по высказываниям. Среднее по высказываниям даёт другой (и несравнимый с публикациями) результат.
- Обязательно публиковать **разбивку S/I/D**, а не только WER: у моделей с prompt-биасингом растут insertions, у CTC — deletions.

### 3.2 Термины: recall / precision / Latin-form accuracy

Трёхуровневая классификация каждого вхождения термина из `terms[]`:

| Класс | Определение | Что значит |
|---|---|---|
| `exact_latin` | гипотеза содержит термин латиницей в написании из `accept` | цель |
| `translit` | гипотеза содержит кириллический транслит из `accept_translit` | «понял, но записал не тем алфавитом» |
| `corrupt` | термин присутствует, но искажён (edit distance ≤ 2 по нормализованной форме) | «услышал, но не распознал» |
| `miss` | термина нет в окне ±N слов | потеря |

Метрики:
- **Term Recall (exact)** = `exact_latin / |terms|` — главная метрика.
- **Term Recall (any)** = `(exact_latin + translit + corrupt) / |terms|` — «услышала ли вообще».
- **Latin-form accuracy** = `exact_latin / (exact_latin + translit)` — «если услышала, записала ли латиницей». Отделяет проблему словаря от проблемы алфавита.
- **Term Precision** = `correct_terms_in_hypothesis / all_term_like_tokens_in_hypothesis` — ловит галлюцинации терминов (модель «вставляет» `kubernetes` там, где его не было). Считать по списку терминов, ищущемуся в гипотезе.
- **Term F-score** — гармоническое.

Окно сопоставления: ±3 слова от позиции термина в референсе, выравнивание по Levenshtein на уровне слов. Это принципиально отличается от `\b…\b`-подхода FluidAudio (см. таблицу проверки) — там позиция не учитывается и термин, случайно попавший в другое место, засчитывается как TP.

### 3.3 Пунктуация и регистр

- **Punctuation F1** по классам `,` `.` `?` `:` `—` — precision/recall/F1 отдельно по каждому, затем macro. Методика сравнима с GigaAM evaluation (там считают F1 по запятой/точке/вопросу).
- **Case accuracy** для терминов: доля терминов, у которых регистр совпал с `accept` (`Kubernetes` vs `kubernetes`). Для остального текста регистр не мерить — русская модель с lowercased-выходом иначе получает незаслуженный ноль.
- **Sentence-boundary F1**: границы предложений как точки/вопросы; нужна, чтобы отделить «пунктуация есть, но не там» от «пунктуации нет».
- Для стриминга — **плотность пунктуации** (знаков на 100 слов) в первой и последней трети длинной сессии: у Nemotron документировано падение при малых чанках (FluidAudio `NemotronMultilingual.md:201`), это надо ловить.

### 3.4 Стриминг

| Метрика | Определение | Как мерить |
|---|---|---|
| **First-partial latency** | от первого кадра PCM до первого непустого `partial` | таймстемп на клиенте, N≥100 попыток, p50/p95 |
| **Final latency (tail)** | от последнего кадра речи (по VAD-end) до `final` | то же; отдельно для «конец фразы» и «конец сессии» |
| **Endpoint latency** | от фактического конца речи (разметка) до `vad.end`/`eot` | против ручной разметки концов на 100 фразах |
| **Partial stability / flicker** | число правок уже «стабильного» префикса на 100 слов; и «stable prefix length» — сколько символов от начала не менялось до final | сравнение последовательных partial'ов по общему префиксу |
| **RTF** | время инференса / длительность аудио | в том же прогоне, что качество (инвариант лидерборда) |
| **Chunk-drop rate** | доля кадров, не обработанных за бюджет (300 мс и т. п.) | счётчик в раннере |

Flicker — единственная метрика, которую нельзя взять из готовых харнессов: её надо писать. Два взаимодополняющих определения, оба считать:

1. **Retraction (откат согласованного префикса).** Для сессии partial'ов $p_1 \dots p_k$ и финального $f$, где $LCP(a,b)$ — длина общего префикса:
$$\text{retraction} = \sum_{i=2}^{k} \max\bigl(0,\; LCP(p_{i-1}, f) - LCP(p_i, f)\bigr)$$
Смысл: сколько символов, которые уже были верны относительно финала, partial «отозвал». Нормируется на 100 слов финального текста.
2. **Churn (дрожание между соседними partial'ами).**
$$\text{churn} = \frac{1}{k-1}\sum_{i=2}^{k} \Bigl(1 - \frac{LCP(p_{i-1}, p_i)}{\max(|p_{i-1}|, |p_i|)}\Bigr)$$
Смысл: какая доля уже выданного текста переписывается на каждом шаге. Высокий churn при низком retraction — «переписывает, но в итоге правильно»; это приемлемо. Высокий retraction — UX-провал: пользователь видит, как правильный текст исчезает.

Оба числа считать на ≥ 50 фразах, p50/p95.

### 3.5 Диаризация и speaker-ID

- **DER** с collar 0.25 с (как в `DiarizationBench`), с разбивкой miss / false-alarm / confusion. Обязательна разбивка: DER 20 % из-за confusion — совсем другой дефект, чем из-за miss.
- **JER** — как в том же харнессе.
- **DER по числу спикеров** (2/3/4) — харнесс уже умеет группировать.
- **Speaker-ID EER между встречами**: enrollment по одной встрече (≥ 30 с чистой речи), проверка на другой. Считать на ≥ 40 парах «тот же / разные», иначе ДИ бессмысленный. Это метрика для `/v1/speakers/match` и `/v1/embeddings/speaker`.
- **Diarization latency** для стриминговой диаризации: задержка появления спикера относительно его первой реплики.

### 3.6 VAD и EOT

- **VAD**: frame-level precision/recall/F1 против ручной разметки речи на 30 мин; отдельно **false-trigger rate на тишине** (срабатываний в минуту) и **hangover** (задержка закрытия).
- **EOT (end-of-turn)**: latency от конца реплики до события + **false-EOT rate** (событие сработало, а человек продолжил). Второе важнее первого: ложный EOT ломает диалог сильнее, чем задержка `[INFERENCE]`.

### 3.7 Галлюцинации и устойчивость к неречевым сегментам

- **Hallucination rate** на 10 мин чистой тишины, 5 мин музыки, 5 мин шума: доля сегментов с непустым текстом. Whisper и LLM-подобные модели (Qwen3-ASR) — в первую очередь.
- **Repetition rate**: доля сегментов с повтором одной фразы ≥ 3 раз подряд.

## 4. Функциональные и контрактные тесты API

### 4.1 Контрактные (не зависят от модели, гоняются на заглушке)

1. **Схема**: каждый ответ валидируется против JSON Schema из репозитория (`/v1/transcribe`, `/v1/vad`, `/v1/diarize`, `/v1/embeddings/speaker`, `/v1/speakers/match`, `/v1/models*`, `/v1/ps`, `/v1/health`, `/v1/capabilities`).
2. **Ошибки**: единый формат (RFC 9457 `application/problem+json`), одинаковый словарь `code` в HTTP и WS, `code` не меняется между версиями (проверка — golden-файл со списком кодов).
3. **Версионирование**: handshake WS содержит версию протокола; сервер отвергает неизвестную мажорную версию с `unsupported_protocol_version`, а не молча деградирует.
4. **Идемпотентность**: повторный `POST /v1/models:pull` с тем же id не создаёт второй артефакт; `DELETE` несуществующей модели — `404` с кодом, повторный `DELETE` — тоже `404` (не `500`).
5. **Отмена**: `POST /v1/transcribe` с клиентским разрывом соединения → сессия завершается, ресурсы освобождаются (проверяется по `/v1/ps` и по отсутствию роста памяти).
6. **Backpressure**: при превышении лимита одновременных сессий — `429` с `Retry-After`, а не блокировка или OOM.
7. **Модель указывается явно**: запрос без `model` → `400 missing_model`; неизвестная модель → `404 model_not_found` с подсказкой списка. Runtime **никогда** не подставляет модель сам (это инвариант из постановки).
8. **Streaming-протокол**: порядок событий (`partial*` → `final`, `vad.start`/`vad.end` парные), монотонность `revision`, отсутствие `final` без предшествующего `partial` (если не пустая речь).
9. **Бинарный фрейминг WS**: неверный заголовок → `error` событие + закрытие с кодом, а не падение воркера.

### 4.2 Функциональные (с реальной моделью, smoke)

- batch: 1 файл WAV → текст непустой, длина в разумных пределах;
- стриминг: тот же файл по 100-мс кадрам → финальный текст близок к batch (расхождение WER ≤ 2 п.п. `[предлагаемый порог]`);
- VAD: файл с 5 с речи + 5 с тишины → ровно один `vad.start`/`vad.end` в правильных местах (±150 мс);
- диаризация: 2-спикерный файл → 2 кластера, DER ≤ 30 % `[предлагаемый]`;
- embeddings: один и тот же файл дважды → cosine ≥ 0.999 (детерминизм);
- `match`: тот же спикер из другого файла → score выше, чем для чужого (проверка направления, не абсолютного порога).

## 5. Конкурентность, память, простой

### 5.1 Сценарии смешанной нагрузки

Матрица (каждый сценарий — отдельный прогон, 5 минут):

| # | Нагрузка | Что проверяет |
|---|---|---|
| C1 | 1 стриминг | базовые латентности |
| C2 | 4 стриминга одной модели | масштабирование и деградация |
| C3 | 4 стриминга разных моделей | стоимость переключения/сосуществования |
| C4 | 1 стриминг + 1 batch (10-мин файл) | **главный сценарий**: деградация realtime при batch-фоне |
| C5 | 4 стриминга + 2 batch | насыщение |
| C6 | 8 стримингов | предел и поведение при отказе (429 vs деградация) |

### 5.2 Метрики

- **Латентность на кадр**: p50/p95/p99 от приёма кадра до `partial`. p99 обязателен — средние скрывают «залипания».
- **Realtime factor под нагрузкой**: `RTF_C4 / RTF_C1` — во сколько раз падает realtime при batch-фоне. Это число прямо отвечает на требование «минимальные накладные расходы».
- **Джиттер** между кадрами (std) — для аудио-конвейера важнее средней.
- **Пропускная способность batch** (секунд аудио в секунду) при 1, 2, 4 конкурентных batch.
- **Справедливость**: разброс латентности между 4 одинаковыми стримингами (max/min p95) — starvation одного из них.
- **CPU**: `ps -o %cpu` или `proc_pid_rusage`; суммарно по дереву процессов воркеров, отдельно control plane.

### 5.3 Память

- **`phys_footprint`** (не RSS) — как в `Memory.swift` speech-swift, с `ledger_phys_footprint_peak` для пиков. Команда: `footprint <pid>` (macOS) или `task_info(TASK_VM_INFO)`.
- Три состояния: (1) после старта без моделей, (2) после загрузки модели без инференса, (3) пик при инференсе.
- **Возврат после unload**: `POST /v1/models/{id}:unload` → `phys_footprint` возвращается к (1) с точностью `[предлагаемый порог]` ≤ 10 % или ≤ 150 МБ (что больше). Не возвращается — значит утечка или кэш MLX/CoreML не освобождён (известная проблема: MLX Metal cache и CoreML plans не освобождаются между движками — прямо задокументировано в speech-swift `asr-wer.md`).
- **Стоимость второй сессии на той же модели**: Δ памяти при C2 − C1. Должна быть << размера весов (общие веса) — это и есть проверка требования «переиспользование весов».
- **Стоимость второй модели**: Δ памяти при C3 − C2.

### 5.4 Idle-накладные

- **CPU wakeups за 60 с простоя**: `powermetrics --samplers tasks -i 1000 -n 60` (нужен sudo) или `top -l 60 -pid <pid> -stats cpu`. Цель `[предлагаемая]`: < 0.1 % CPU и < 5 wakeups/с на control plane при отсутствии сессий.
- **RSS/phys_footprint в простое после прогрева** — не должен расти (проверка на утечку таймеров).
- **Поведение TTL**: после истечения `keep_alive` модель выгружается, память возвращается; повторный запрос — холодная загрузка (мерить её отдельно: это UX-метрика).

## 6. Устойчивость

| # | Инжекция | Ожидание | Как проверять |
|---|---|---|---|
| F1 | `kill -9` воркера во время стриминга | клиент получает `error`-событие с кодом, сессия помечается failed, supervisor перезапускает воркер; следующий запрос работает | скрипт: старт стриминга → kill → проверка события → новый запрос |
| F2 | `kill -9` control plane | launchd поднимает; клиенты получают разрыв; состояние моделей восстанавливается по lease-файлам (или чистый старт — задокументировать) | 10 циклов, проверка отсутствия «зомби»-воркеров |
| F3 | Обрыв WS-соединения клиентом | сессия закрывается ≤ 1 с, память возвращается | сравнение `/v1/ps` и footprint до/после |
| F4 | Повреждённый артефакт модели | `pull`/`load` отвергает по sha256 с кодом `artifact_corrupt`, не падает | подменить байт в blob → load |
| F5 | Нехватка диска при `pull` | понятная ошибка, частичный файл не остаётся (или помечен), существующие модели целы | заполнить диск (или quota-образ), pull |
| F6 | Нехватка памяти при загрузке | отказ с `insufficient_memory`, а не OOM-kill control plane; уже загруженные модели выживают | запустить 3 большие модели подряд при малом лимите |
| F7 | Медленный клиент (не читает поток) | backpressure, буфер ограничен, память не растёт | клиент читает 1 кадр/с |
| F8 | Soak 24 ч | нет роста памяти, нет роста числа потоков/файловых дескрипторов, нет дрейфа латентности | `lsof -p`/`ps -M` каждый час + прогон короткого eval в начале и конце |
| F9 | Смена сети (loopback недоступен) | понятная ошибка клиенту, без зависания | — |
| F10 | Часы/время: смена системного времени | таймстемпы событий монотонны (использовать `mach_continuous_time`) | — |

Soak 24 ч — единственный тест, который нельзя ускорить. Его бюджет: ~24 ч машинного времени на релиз-кандидат, не на каждый коммит.

### 7.1 Как это запускается (конкретно)

**Batch WER/термины** — датасет подаётся манифестом, код харнесса не меняется:

```bash
# manifest.tsv: <путь к wav>\t<референс>  (относительные пути от каталога манифеста)
.build/release/asr-bench \
  --dataset ru-it/test-manifest.tsv \
  --engines qwen3-mlx-1.7b-8bit qwen3-coreml parakeet nemotron \
            whisperkit-large-v3-turbo whisper-asr-turbo omnilingual \
  --isolated \
  --output ru-it-test-2026-10-25.json
```

**Ограничение, которое надо знать заранее:** в `asr-bench` **нет движка sherpa-onnx** — ID движков перечислены в `Engine.swift` (`qwen3-*`, `parakeet`, `nemotron*`, `omnilingual*`, `whisper-asr-turbo`, `whisperkit-*`, `cohere-*`, `kyutai-*`, `moss-*`), GigaAM v3 и T-one среди них отсутствуют. Значит:
- модели speech-swift/FluidAudio/WhisperKit меряются `asr-bench` напрямую;
- GigaAM v3 / T-one / Voxtral Realtime меряются **отдельным раннером** (sherpa-onnx CLI / Python), который пишет TSV `<id>\t<гипотеза>`;
- обе ветки скармливаются **одному** Python-скорингу (WER + термины + пунктуация) — так числа сравнимы, потому что нормализатор и токенизация одни и те же.

Это архитектурное решение методики: **раннер движка и скорер разделены**. Иначе получим три разных WER-арифметики и спор о цифрах вместо выбора модели.

Терминные метрики считаются по `report.json` → `results[*].utteranceResults[*].{reference,hypothesis}` (поля проверены, см. таблицу), либо по TSV от внешнего раннера — формат один и тот же.

**Важная ловушка:** `Normalizer.normalize` в `asr-bench` приводит к lowercase и вырезает пунктуацию **до** подсчёта WER. Поэтому:
- WER из отчёта — уже нормализованный (это то, что нужно для §3.1);
- `exact_latin` / case accuracy по нему считать **нельзя** — они должны считаться по сырым `hypothesis` из `utteranceResults`, своей реализацией (§3.2);
- нормализатор содержит английские contraction-правила и не знает `ё`/русских чисел — для публикации чисел, сравнимых с вендорскими, нужен наш нормализатор, а результат харнесса использовать только как кросс-проверку.

**Диаризация и VAD** — ещё два готовых исполняемых таргета в том же репозитории (`diarization-bench`, `vad-bench`), оба принимают манифест `<audio>\t<reference>` с RTTM или `start/end`-текстом:

```bash
.build/release/diarization-bench --dataset ru-it/r2-manifest.tsv --collar 0.25 --output r2-der.json
.build/release/vad-bench         --dataset ru-it/vad-manifest.tsv --output vad.json
```

`vad-bench` даёт frame-level precision/recall/F1 (и F1 по файлу), умеет пороги Silero onset/offset и min-speech/min-silence — то есть §3.6 покрывается без своего кода.

**Воспроизведение power-симуляции** (объём набора): `python3 /tmp/srr/probe/V8EvalPlan/bootstrap_power.py` — 69 с на M-серии, numpy 2.5.4.

## 8. Решающие эксперименты (≤10, по убыванию влияния на решение)

Критерий порядка — **влияние = (насколько меняет архитектуру) × (насколько дорого отменить решение)**. Эксперимент, чей исход меняет политику (TTL), стоит ниже, чем эксперимент, меняющий число процессов в системе.

| # | Эксперимент | Что решает | Цена ошибки | Стоимость |
|---|---|---|---|---|
| E1 | Латиница в выходе | нужен ли биасинг как слой; какая модель основная | высокая (перевыбор модели) | 1 д |
| E2 | Конкурентность на одной модели | модель воркера: батчинг / пул инстансов / второй процесс | высокая (переделка супервизора) | 2 д |
| E3 | Стриминг vs batch | один движок на оба режима или два | высокая (число воркеров) | 1–2 д |
| E4 | e2e-нормализация | нужен ли отдельный пунктуатор/ITN | средняя (+1 компонент) | 0.5 д |
| E5 | Галлюцинации на неречи | VAD в критическом пути или опция | средняя (латентность+архитектура) | 0.5 д |
| E6 | Транслит → латиница | пост-процессор в runtime или в приложении | средняя (граница API) | 1 д |
| E7 | Возврат памяти после unload | срок жизни воркера, обязанности супервизора | средняя | 0.5 д |
| E8 | Деградация realtime при batch | нужен ли приоритетный планировщик | низкая-средняя | 1 д |
| E9 | Диаризация на русских встречах | одна модель на диаризацию+эмбеддинги или две | низкая-средняя | 2 д |
| E10 | Холодная загрузка и простой | политика TTL/keep_alive | низкая (меняется конфигом) | 0.5 д |

### E1. Латиница: может ли модель вообще выдать термин латиницей
**Вопрос:** какая доля IT-терминов воспроизводится латиницей (`exact_latin`) у GigaAM v3 (ctc/rnnt/e2e), Whisper large-v3/turbo, Parakeet v3, Canary v2, Nemotron 3.5, Voxtral Realtime, Qwen3-ASR, T-one?
**Данные:** 150 высказываний R1+R4 из dev, ≥ 400 вхождений терминов.
**Метрика:** `exact_latin`, `translit`, `corrupt`, `miss` + Latin-form accuracy.
**Меняет решение:** нужен ли биасинг как обязательный слой и каким механизмом (hotwords vs CTC-WS vs prompt). Если Latin-form accuracy < 50 % — модель не годится как основная для диктовки кода независимо от WER.
**Цена ошибки:** перевыбор основной модели после того, как под неё написан воркер и откалиброван биасинг.
**Стоимость:** 1 день (офлайн, без runtime).

### E2. Стоимость конкурентности на одной модели
**Вопрос:** сколько стоит вторая одновременная сессия на той же модели — по памяти и по латентности — для ONNX (sherpa, N Stream), CoreML (пул инстансов) и MLX (сериализация)?
**Метрика:** Δ `phys_footprint` на сессию, p95 латентности на кадр при 1/2/4 сессиях, RTF.
**Меняет решение:** модель конкурентности воркера (батчинг потоков vs пул инстансов vs второй процесс). Это выбор, который дороже всего переделать позже.
**Цена ошибки:** переписывание супервизора, протокола воркера и admission control.
**Стоимость:** 2 дня (нужен минимальный прототип на каждом движке).

### E3. Стриминг против batch на терминах
**Вопрос:** сколько term recall теряется при переходе на стриминг (Nemotron 160/320/1120 мс, Voxtral 240/480/960 мс, T-one 300 мс) относительно batch-версии тех же моделей?
**Метрика:** term recall + WER на одном наборе, фиксированный chunk/delay.
**Меняет решение:** допустим ли единый движок для batch и стриминга (один воркер) или нужны два разных. Прямо влияет на раздел «Процессы» черновика.
**Цена ошибки:** двойной набор воркеров и двойная стоимость весов в памяти.
**Стоимость:** 1–2 дня.

### E4. Цена e2e-нормализации: WER vs пунктуация/термины
**Вопрос:** сколько WER стоит переход с `gigaam-v3-rnnt` (lowercase, без пунктуации) на `e2e_rnnt` (пунктуация + латиница), и окупается ли это терминами?
**Метрика:** WER (нормализованный) + P-F1 + term recall, три варианта на одном наборе.
**Меняет решение:** нужен ли отдельный слой пунктуации/ITN в runtime. Если e2e проигрывает по WER больше, чем даёт по P-F1 — вводим отдельный пунктуатор, и это +1 компонент в архитектуре и +латентность.
**Цена ошибки:** лишний компонент в критическом пути либо плохой UX диктовки.
**Стоимость:** 0.5 дня.

### E5. Галлюцинации на неречи
**Вопрос:** как часто модели выдают текст на тишине/музыке/шуме?
**Метрика:** hallucination rate на 20 мин неречи (10 тишина / 5 музыка / 5 шум), repetition rate.
**Меняет решение:** обязателен ли VAD-гейт перед ASR в runtime (а не опция). Для Whisper/Qwen3-подобных — почти наверняка да; VAD в критическом пути связывает латентность ASR с VAD-порогами.
**Цена ошибки:** «говорящий» runtime на тишине — худший класс багов для пользователя.
**Стоимость:** 0.5 дня.

### E6. Транслит vs латиница на входе
**Вопрос:** если диктор говорит «кубернетес», должна ли модель писать `kubernetes`? Что реально делают модели?
**Данные:** R4 двойной проход (§2.4, п.2) — 100 команд × 2 произношения.
**Метрика:** матрица «spoken_form × output_form».
**Меняет решение:** нужен ли пост-процессор транслит→латиница в runtime или это ответственность приложения. Матрица, которой нет ни у одного вендора.
**Цена ошибки:** неверная граница API: либо runtime навязывает языковую политику (против принципа «runtime не решает за клиента»), либо приложение получает транслит и вынуждено держать свой словарь.
**Стоимость:** 1 день.

### E7. Возврат памяти после unload
**Вопрос:** возвращается ли `phys_footprint` к базовому после выгрузки модели — для MLX, CoreML, ONNX?
**Метрика:** footprint до загрузки / после загрузки / после unload / после 3 циклов load-unload.
**Меняет решение:** можно ли жить в одном долгоживущем процессе или нужен перезапуск воркера после N выгрузок (и тогда supervisor обязан уметь это делать по расписанию). Известный риск: MLX Metal cache и CoreML plans не освобождаются — прямо задокументировано в speech-swift (`docs/benchmarks/asr-wer.md`, раздел «Reading the memory column»).
**Цена ошибки:** runtime «съедает» память за дни работы, пользователь видит swap.
**Стоимость:** 0.5 дня.

### E8. Деградация realtime при batch-фоне (сценарий C4)
**Вопрос:** насколько падает p95 латентности стриминга, когда параллельно идёт 10-минутный batch на том же движке и на другом?
**Метрика:** `RTF_C4 / RTF_C1`, p95/p99 на кадр.
**Меняет решение:** нужен ли приоритетный планировщик с классами (realtime > interactive > batch) или достаточно FIFO с лимитом. Если деградация < 20 % — планировщик можно не делать в v1 `[предлагаемый порог]`.
**Цена ошибки:** лишняя сложность планировщика либо «залипающий» стриминг при чужой транскрипции.
**Стоимость:** 1 день после E2.

### E9. Диаризация на русских встречах
**Вопрос:** какой DER даёт FluidAudio (pyannote community-1 + WeSpeaker) и Sortformer/Nemotron на русских созвонах с 2–4 спикерами и перекрытиями?
**Данные:** 10 встреч R2 с RTTM; до их записи — `ivkond/synthetic-speech-diarization-ru` как stopgap.
**Метрика:** DER (miss/FA/confusion), JER, DER по числу спикеров; + speaker-ID EER между встречами.
**Меняет решение:** тянет ли одна модель обе задачи (диаризация + эмбеддинги) или нужны две; нужен ли streaming-режим диаризации в v1.
**Цена ошибки:** лишний воркер и лишние веса в памяти.
**Стоимость:** 2 дня.

### E10. Холодная загрузка и стоимость простоя
**Вопрос:** сколько занимает холодная загрузка каждой модели и сколько CPU/wakeups потребляет runtime в простое?
**Метрика:** время до первого результата после `load` (p50/p95, 10 повторов), CPU % и wakeups/с в простое 60 с.
**Меняет решение:** политика TTL/keep_alive и нужен ли прогрев. Для ориентира: в замерах speech-swift кэшированная загрузка WhisperKit Large-v3 Turbo — 7.2 с (и 13.2 с в обратном прогоне), у нативного WhisperASR — 1.3 с.
**Цена ошибки:** низкая — меняется конфигом.
**Стоимость:** 0.5 дня.

**Порядок выполнения:** E1 → E2 → (E3 ∥ E4 ∥ E5 ∥ E6) → E7 → E8 → E9 → E10.
E2, E7, E8 требуют минимального прототипа транспорта; E1, E3, E4, E5, E6, E9, E10 — чистый офлайн на файлах.
Суммарно: ~10 рабочих дней, из них ~4 — на прототип.

**Правило остановки:** если E1 показывает, что ни одна модель не даёт Latin-form accuracy выше 50 %, дальше идти нельзя — сначала решается вопрос биасинга (механизм, словарь, возможно дообучение), и только потом всё остальное.

## 9. Приёмка готового runtime (контур B)

Гейты, которые прогоняются на релиз-кандидате. Все пороги — **предлагаемые**, подлежат калибровке после первых трёх прогонов (принцип: сначала измерить, потом зафиксировать).

### 9.1 Качество (регрессия, ru-IT test, заморожен)

| Метрика | Предлагаемый гейт | Обоснование |
|---|---|---|
| WER (нормализованный) | не хуже baseline − 0.5 п.п. | 0.5 п.п. — ниже разрешения набора (§2.6), значит шум допустим |
| Term recall (exact) | не хуже baseline − 2 п.п. | ±4.5 п.п. ДИ при 400 вхождениях → 2 п.п. внутри шума, но не больше |
| Latin-form accuracy | не хуже baseline − 2 п.п. | то же |
| P-F1 (macro) | не хуже baseline − 2 п.п. | — |
| Hallucination rate на неречи | ≤ 1 % сегментов | `[предлагаемый]` |
| CER | не хуже baseline + 0.5 п.п. | страховка от слипания слов |

Baseline обновляется только по решению, с записью причины (иначе «ползучая деградация»).

### 9.2 Латентность (M-серия Apple Silicon, `[предлагаемые]`)

| Метрика | Гейт |
|---|---|
| first-partial p95 | ≤ 500 мс |
| final latency (tail) p95 | ≤ 300 мс после VAD-end |
| p99 латентности на кадр (стриминг) | ≤ 1.5 × chunk |
| RTF batch (10-мин файл) | ≤ 0.3 |
| `RTF_C4 / RTF_C1` | ≤ 1.5 |

### 9.3 Память и простой

| Метрика | Гейт |
|---|---|
| phys_footprint control plane (idle) | ≤ 150 МБ |
| возврат после unload | ≤ max(10 %, 150 МБ) от базового |
| Δ памяти на вторую сессию той же модели | ≤ 15 % размера весов |
| CPU в простое | ≤ 0.1 % |
| wakeups/с в простое | ≤ 5 |

### 9.4 Устойчивость

Все F1–F10 из §6 — pass. F8 (soak 24 ч) — только на релиз-кандидат, не на каждый коммит. Критерии: рост `phys_footprint` за 24 ч ≤ 5 %, число fd и потоков стабильно, дрейф p95 латентности ≤ 10 %.

### 9.5 Контракт

Все тесты §4.1 — pass. Плюс: golden-файл со списком `code` не изменился без мажорного бампа версии протокола.

## Неизвестные / что измерить

1. **Есть ли публичный русский IT/code-switching набор** — поиск по HF (`code-switch*`, `russian+asr`) не дал ничего релевантного; остаётся возможность, что он лежит вне HF (Kaggle, Zenodo, внутренние наборы компаний). Проверить точечно, не рассчитывать.
2. **Лицензия Golos** — карточка HF не содержит поля license; нужен первоисточник (Sber) и юридическая оценка.
3. **Лицензия `bond005/podlodka_speech`** — не указана; домен идеальный, но правовой статус неизвестен.
4. **Разрешающая способность метрик на нашем объёме** — оценена симуляцией (§2.6); надо перепроверить на реальных данных после первого прогона (симуляция предполагала lognormal-длины и Gamma-сложность).
5. **Нужен ли парный bootstrap или достаточно независимого** — не мерил; влияет на требуемый объём.
6. **cpWER vs DER для русских встреч с перекрытиями** — какая метрика лучше отражает UX; не проверял.
7. **Стоимость измерения flicker** — нужен ли отдельный протокол partial'ов в API (сейчас черновик даёт `revision` и `stable_prefix_chars`, этого достаточно `[INFERENCE]`).
8. **Воспроизводимость CoreML/MLX между запусками** — детерминизм вывода не гарантирован; надо померить, иначе регрессионные гейты будут шуметь. Не мерил.
9. **Пороговые значения §9** — все предлагаемые; калибровать после 3 прогонов.
10. **Стоимость 24-часового soak в CI** — организационный вопрос (выделенный Mac), не технический.
