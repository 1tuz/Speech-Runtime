# Runtime prototype: проверка архитектурных допущений

Экспериментальный прототип, а не продукт. Он существует, чтобы измерить сквозной путь
«HTTP-клиент → демон → воркер → ANE» и стоимость изоляции процессов, а не чтобы зафиксировать API.

Состав:

| Часть | Язык | Роль |
|---|---|---|
| `daemon/` | Swift 6.4 | loopback HTTP API, токен, каталог моделей, сессии клиента, idle-unload, супервизия воркера |
| `worker/` | Rust (`wavo` 0.4) | загрузка GGUF, очереди interactive/batch, earshot VAD, эндпоинтинг, транскрибация; batch-разрезание длинных файлов на чанки по границам тишины |
| `models.json` | — | объявленные модели, пути и backend (`ane`/`gpu`); пути не коммитятся |

Запуск:

```bash
cd runtime/worker && cargo build --release
cd ../daemon && swift build
cp ../worker/target/release/sr-worker .build/debug/sr-worker
.build/debug/speech-runtime --config ../models.json --port 8477 \
  --worker "$PWD/.build/debug/sr-worker"
```

`backend: "ane"` в `models.json` работает только после подготовки модели для Neural Engine:
wavo строит и компилирует программу в `~/Library/Caches/wavo/`, и без неё загрузка падает с
`the model is not prepared for the Neural Engine`. Подготовка — `wavo pull gigaam-v3
parakeet-ultra` (модели берутся из того же кэша Hugging Face, что указан в `models.json`).
Первая загрузка в новом бинарнике воркера занимает 10–30 с (системная компиляция под ANE),
последующие — десятки миллисекунд; приведённые ниже числа относятся к прогретой загрузке.
Если каталог кэша wavo удалён (например, чистильщиком кэшей), модели нужно подготовить заново.

Клиент `sr` говорит только по HTTP, как стороннее приложение:

```bash
sr health
sr load gigaam
sr transcribe file.wav --model gigaam --priority batch
sr stream file.wav --model gigaam --realtime 1   # подача в темпе реального времени
```

## Измерения

Apple M4, 16 ГБ, macOS 27.2, GigaAM v3 e2e-RNNT Q8_0 на ANE. Дата указана там, где значение
менялось; артефакты и команды воспроизведения — в `FINAL_VALIDATION.md`.

| Что | Значение | Условие |
|---|---|---|
| Загрузка модели | 45–105 мс | `ane`, тёплый файловый кэш |
| Батч 20.1 с аудио | ASR 76 мс, wall 174 мс, RTF 0.004 | `priority=batch` |
| 1 клиент 1×, 60 мин | e2e 469 / 517 мс p50/p95: тишина 320 мс включена в метрику, очередь 0, ASR 54 / 134 | 2026-11-06, 671 финал |
| 4 клиента 1× без батча | очередь 75 / 176 мс, e2e 530 / 690 мс, 384 финала, 0 ошибок | 2026-11-06, `soak multiclient` |
| 60 мин 1×, память | демон 11.1 → 23.0 МиБ, воркер 13.8 → 29.4 МиБ RSS; дрейф ≈ 63 КиБ/мин после прогрева | 149 сэмплов каждые 30 с |
| 4 клиента 1× + батч (разрезание) | очередь p95 157 мс, e2e p95 605 мс, 84 финала, 0 ошибок — критерий p95 < 2000 мс **выполнен** | 2026-11-06, batch-чанки 10 с, 219 задач; `soak multi-4-batch-sliced-1x.json` |
| 1 клиент 1× + батч (разрезание) | очередь p95 39 мс, e2e p95 584 мс | 2026-11-06, 223 задачи; `soak multi-1-batch-sliced-1x.json` |
| Разрезанный батч: идентичность | 25-мин WAV, 148 частей: текст и 9737 токенов с таймстампами байт-в-байт равны монолитному прогону тех же весов | 2026-11-06, `batch-split-compare-25min.json` |
| VAD-конвейер на естественной записи | 172 с «2-one-to-one»: WER 3.57 % (батч тех же весов 6.12 %), 0 слов потеряно на границах | 2026-11-06, `pipeline-natural-*.json`, эталоны `unverified` |
| 4 клиента 1× + батч (до разрезания) | очередь p95 2399 мс, e2e p95 3321 мс — устранено разрезанием батча на чанки по границам тишины (строки выше) | 139 батч-задач, одна in-flight |
| ANE, отдельно рассчитанный `neural_footprint` | 243 → 258 МиБ, 0 после выгрузки, пик 938 МиБ на двух моделях | `memory_probe`, свои процессы |
| Демон / воркер, footprint | 11.4–12.6 / 2.2 МиБ, стабилизировано | 2026-11-05, после фикса утечки; до фикса +53.7 МиБ за ту же серию |
| Падение воркера | клиент получает `worker exited with status 9`, демон жив, `restarts` 0 → 1, модель догружается | `soak crash` |
| Две модели одновременно | gigaam e2e 89 / 134 мс, parakeet-ultra 190 / 198 мс | p50 / p95 |
| Отмена сессии | снимает очередь, поздних финалов 0, `streams` → 0 | `soak cancel` |

Прежние **133 мс** — это время от срабатывания эндпоинтера до финала при 4× подаче, а не от
последнего голосового кадра. WER 5.88 % (2026-11-04) относится к одному 47-секундному фрагменту.
Измерение 2026-11-05 — пять клипов Podlodka с невыверенными референсами
(см. `experiments/corpus/references-policy.md`); ни то, ни другое не является бенчмарком продукта.

Рост RSS демона в длительной нагрузке объяснён и устранён. 3000 запросов `/health` поднимали RSS
с 111 008 до 164 880 КиБ; внешняя атрибуция (`heap`, `malloc_history`) показала один блок
`NSConcreteData` 20 КиБ на каждый IPC-ответ: `availableData` читался вне пула автоосвобождения.
Теперь каждый ответ обёрнут в `autoreleasepool` — та же серия даёт +4.6 МиБ вместо +53.7 МиБ,
в простое +0.1 МиБ. Команды: `python3 -m runtime_eval.memory_matrix <phase>` и
`python3 -m runtime_eval.soak long-session ...` из каталога `experiments`.

## Что было сломано и исправлено при проверке

Дефекты найдены измерениями, а не чтением кода:

1. `session_open`/`session_audio`/`session_end` не несли `id`, ответы приходили с `id: null`, и демон
   отваливался по таймауту. Идентификаторы теперь возвращаются на всех операциях.
2. `RuntimeClient.streamAudio` отправлял сырой `f32le` без `X-Sample-Format`, демон пытался разобрать
   его как WAV.
3. Метрика «эндпоинт → финал» смешивала аудио-время и wall-clock (при 4× подаче давала −14.9 с).
   Теперь позиция аудио переводится в часы по контрольным точкам подачи.
4. `FileHandle.bytes.lines` на stdout воркера задерживал готовую строку до 30 с на pipe, что давало
   ложные таймауты запросов. Чтение вынесено в отдельный поток с упорядоченной передачей строк.
5. Запись в лог из нескольких задач шла без синхронизации и портила строки.
6. Тесты эндпоинтера кодировали расчёт, несовместимый с кадром 16 мс; переписаны на проверку
   инвариантов (`pcm = (end − start)`, `end = last_voice + post_roll`).
7. Если постановка хвостовой задачи на `session_end` падала, клиент получал два ответа (`error` и
   `ok`), а в потоке появлялся `utterance` без последующего `final`. Теперь ответ ровно один,
   хвост приходит `final` перед `ended`, причина — в `end_reason`.
8. Ошибки сессии в воркере возвращались без `request id` и не сопоставлялись с запросом; отказ
   постановки задачи в очередь был невидим, счётчиков ожидающих reply, event-waiters, буферов и
   завершающихся сессий не было. Всё это попало в `/health` вместе с памятью воркера.
9. HTTP-парсер проверял `Content-Length` только после обработки и принимал `Transfer-Encoding`.
   Границы и лимиты проверяются до диспетчеризации, `Transfer-Encoding` отвергается.

## Проверенные инварианты

| Проверка | Результат |
|---|---|
| Неизвестная модель | `{"error":"unknown model nope; declared models": [...]}`, без подмены |
| Запрос без токена и с неверным токеном | 401 |
| Аудио и транскрипты в логе | не пишутся (поиск по логу и по канареечной строке) |
| Отмена сессии | `session_cancel` снимает очередь, помечает задачи отменёнными, поздних финалов 0 |
| Выгрузка модели | активная сессия получает отказ; после завершения модель выгружается |
| Медленный клиент | при 4× подаче очередь и `streams` возвращаются к базовому уровню |
| Утечка на IPC-ответ | 3000 ответов: +4.6 МиБ (было +53.7), кэш освобождён после ответа |
| Хвост реплики на `session_end` | `final` приходит до `ended`, `end_reason` в событии |
| Падение воркера | демон жив, `restarts` растёт, клиент видит явную ошибку, модель догружается |

Проверены отдельные прогоны четырёх клиентов с batch и без, двух моделей, аварийного завершения
воркера, отмены и медленного клиента. Не проверены исчерпание памяти, обновление модели под
активной сессией и возврат памяти ANE после длительной нагрузки.

## Ограничения

Прототип не претендует на финальный контракт: имена полей, формат событий и схема конфигурации
выбраны для измерений. Транспорт — loopback HTTP с bearer-токеном; WebSocket, LaunchAgent и
разделение воркеров по движкам не проверялись и не объявляются решением.
